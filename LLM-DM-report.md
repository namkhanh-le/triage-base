
# LLM and Decision Model Evaluation Report

## 1. Objective

This project evaluates three strategies for support-ticket triage:

- **LLM:** the language model classifies the ticket and provides an explanation.
- **DM:** a Decision Model selects the category, priority, and whether human review is required.
- **DM + LLM:** the Decision Model selects the category and priority; the LLM provides a natural-language explanation. Human review is enabled if either model flags it.

The goal is to compare classification accuracy, latency, token usage, estimated cost, and operational reliability.

## 2. Decision Model research and selection

The Decision Model options considered were:

- **Decision 3.0 (vLLM Semantic Router):** a hosted decision API that supports typed choices and yes/no questions.
- **Jev (TypeSafe):** a hosted decision-model API using typed decisions.
- **OpenAI Decisions API:** a decision endpoint separate from ordinary chat completions.
- **Cloudflare Clef:** another decision-model option identified in the course material.

### Selected model

This implementation uses **Decision 3.0**, configured as `vllm-sr/d3-flash`, through the `https://decision.vllm-sr.ai/v1/systemone` endpoint.

Reasons for selection:

1. It offers hosted access for experimentation, subject to its current usage limits.
2. Its typed-choice interface fits the predefined support categories and priorities.
3. It supports a yes/no question for human-review decisions.
4. It returns structured answers and input-token usage.
5. It can be called from the server without exposing the API key in the browser.

References:

- https://decision.vllm-sr.ai/
- https://decision.vllm-sr.ai/docs
- https://typesafe-jev.com/en/guides/api/

## 3. Integration design

### LLM-only strategy

The existing NVIDIA-hosted LLM receives the ticket subject and body. Its response is parsed as JSON and validated using Zod. It returns the category, priority, human-review decision, and a short explanation.

### Decision Model-only strategy

The Decision Model receives the ticket as state and answers typed questions for category, priority, and human review. The application validates the response before using it.

The Decision Model's explanation is generated by the application from the selected answers and review probability; it is not a free-form explanation written by the Decision Model.

### Hybrid strategy

The Decision Model determines the category and priority. The LLM supplies an explanation. If either model requests human review, the final result requires human review.

The hybrid approach uses the Decision Model for bounded classification choices and the LLM for natural-language explanation. Whether this combination improves performance must be established through evaluation.

## 4. Evaluation method

The application supports two datasets:

- **Labelled dataset:** 100 support tickets with reference categories, priorities, and human-review labels.
- **Unlabelled dataset:** 500 support tickets for examining predictions, token usage, and latency without calculating ground-truth accuracy.

The smoke-test runner selects a random sample and records:

- Requested sample size, completed tickets, and failures.
- Strategy and model identifier.
- Category, priority, human-review, and all-fields accuracy for labelled data.
- Counts of classification mismatches.
- Average latency per successfully classified ticket.
- Input, output, and total token usage.
- Estimated cost based on the configured pricing rates.

Accuracy is calculated by comparing model predictions with the supplied labels. Agreement between two models is not, by itself, evidence of correctness.

For a fair comparison, run each strategy on the same dataset with the same sample size. Random samples can differ between runs, so larger and repeated evaluations provide stronger evidence.

## 6. Limitations

- The labelled dataset may contain ambiguous examples or imperfect reference labels.
- Model predictions and decision probabilities are not guaranteed to be correct.
- The hosted Decision Model may impose quotas, change availability, or change model versions.
- Estimated cost depends on configured pricing and must not be treated as a provider invoice.
- The Decision Model's generated review probability is thresholded at 0.5 in this implementation; that threshold has not necessarily been calibrated for this dataset.
- The hybrid strategy combines predictions from two services, so a failure of either service can prevent the run from completing.
- Human review remains important for sensitive, unclear, or high-impact tickets.
